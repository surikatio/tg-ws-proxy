# Прозрачный режим: Telegram у всех в сети без настройки клиентов

Обычный режим требует, чтобы на каждом устройстве был прописан прокси. Прозрачный работает иначе: трафик к Telegram заворачивается на сервер маршрутизацией, а клиенты ничего не знают о прокси и ничего не настраивают. **Весь остальной трафик идёт напрямую и сервера даже не касается.**

> [!IMPORTANT]
> Нужен Linux-сервер (используется netfilter, на Windows это не работает) и роутер, на котором можно прописать статические маршруты.

## Как это работает

```
Телефон → роутер ─┬─ трафик к Telegram → сервер → WebSocket → Telegram DC
                  └─ весь остальной трафик → напрямую в интернет
```

Роутер знает, что подсети Telegram достижимы «через сервер», и отправляет к нему только их. На сервере netfilter перехватывает эти пакеты и отдаёт их прокси, который мостит соединение через WebSocket.

Обычный MTProto-прокси так не умеет: клиент, не знающий о прокси, шифрует handshake без секрета. В прозрачном режиме прокси разбирает именно такой handshake — номер дата-центра берётся из самого пакета.

## Шаг 1. Сервер

```bash
# разрешить пересылку чужих пакетов
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-tgwsproxy.conf

# правила перехвата
sudo packaging/transparent-nft.sh apply

# сам прокси
tg-ws-proxy --transparent
```

`--transparent` сам слушает `0.0.0.0` (перенаправленные пакеты приходят с интерфейса, смотрящего в сеть) и не требует секрета.

Скрипт заворачивает только порты `443, 80, 5222` в подсетях Telegram. Список подсетей зашит в `packaging/transparent-nft.sh` — сверяйте его с https://core.telegram.org/resources/cidr.txt, адреса меняются.

## Шаг 2. Роутер

Пусть сервер — `192.168.0.10`. Нужно прописать маршруты к подсетям Telegram через него.

**OpenWrt** (Network → Static Routes, или в `/etc/config/network`):

```
config route
    option interface 'lan'
    option target '149.154.160.0/20'
    option gateway '192.168.0.10'
```

…и так для каждой подсети: `91.105.192.0/23`, `91.108.4.0/22`, `91.108.8.0/22`, `91.108.12.0/22`, `91.108.16.0/22`, `91.108.20.0/22`, `91.108.56.0/22`, `95.161.64.0/20`, `149.154.160.0/20`, `185.76.151.0/24`.

**MikroTik:**

```
/ip route add dst-address=149.154.160.0/20 gateway=192.168.0.10
```

**Keenetic:** «Маршрутизация» → «Добавить маршрут» → маршрут до подсети, шлюз `192.168.0.10`.

**Если роутер не умеет статические маршруты**, есть два обходных пути:

- **DHCP option 121** (classless static routes) — маршруты раздаются клиентам при подключении к Wi-Fi. Умеет OpenWrt и часть прошивок; Android и Windows это уважают, iOS — не всегда.
- **Назначить сервер шлюзом по умолчанию** на конкретном устройстве вручную. Тогда через сервер пойдёт весь трафик этого устройства, а не только Telegram.

## Шаг 3. Проверка

На клиенте (Telegram при этом должен быть **без** настроенного прокси):

```bash
# маршрут должен идти через сервер
ip route get 149.154.167.51
traceroute -n -T -p 443 149.154.167.51
```

На сервере смотрите лог — должны появляться соединения:

```
[192.168.0.55:41234] DC2 -> wss://kws2.web.telegram.org/apiws via 149.154.167.220
```

Раз в минуту печатается сводка, в ней полезны `ws=` (сколько соединений ушло через WebSocket) и `pass=` (сколько прошло насквозь как не-MTProto).

## Если что-то ломается

Прозрачный режим тем и коварен, что на клиенте прокси не виден и непонятно, почему Telegram молчит. Быстрый откат — снять правила и маршруты:

```bash
sudo packaging/transparent-nft.sh delete
```

Что стоит знать заранее:

- **IPv6 идёт мимо.** Правила только для IPv4, и если у клиента есть IPv6-маршрут до Telegram, он уйдёт напрямую. Либо отключите IPv6 в сети, либо добавьте аналогичные правила для `ip6`.
- **Не-MTProto трафик не ломается.** В подсетях Telegram есть и веб/CDN. Такие соединения прокси распознаёт (handshake не совпал) и пробрасывает на исходный адрес как есть — в статистике это `pass=`. Работает это за счёт `SO_ORIGINAL_DST`, то есть только при перехвате через netfilter.
- **Сервер становится единой точкой отказа.** Выключился сервер — Telegram у всех перестал работать, пока не убрать маршруты на роутере. Для критичных сценариев лучше обычный режим со ссылкой.
- **Список подсетей устаревает.** Если Telegram добавит диапазон, трафик к нему пойдёт мимо прокси.
- **Fake TLS несовместим** с прозрачным режимом: клиент шлёт обычный обфусцированный MTProto, поэтому `--fake-tls-domain` вместе с `--transparent` не принимается.

## Сравнение с обычным режимом

| | Прозрачный | Обычный (ссылка) |
|---|---|---|
| Настройка на клиенте | не нужна | прописать прокси один раз |
| Работает вне дома | нет | да, если сервер доступен |
| Нужен доступ к роутеру | да | нет |
| Гостевые устройства | подхватываются сами | нужно дать ссылку |
| Диагностика | сложнее | понятнее |

Режимы не исключают друг друга: можно держать прозрачный для домашних устройств и раздавать `t.me/proxy`-ссылку тем, кто подключается извне. Для этого запустите два экземпляра на разных портах — например, прозрачный на `1443` и обычный на `1444`.
